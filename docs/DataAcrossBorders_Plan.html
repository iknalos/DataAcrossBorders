DataAcrossBorders

Project Analysis & Build Plan — Federated Medical Imaging Search
Repository: iknalos/DataAcrossBorders  |  Prepared: July 25, 2026  |  Event: The Open Accelerator Healthcare Hackathon — Track 1

1. Executive Summary

The repository currently contains only the hackathon boilerplate: a deliberately minimal FastAPI application that simulates one siloed hospital database node. Run three times on different ports, it mimics three disconnected Boston hospitals (BCH, MGH, BWH), each holding 900 synthetic radiology study records with no authentication, no search, and fully exposed patient PII.

Nothing of "your solution" exists yet. The entire challenge deliverable — a federated search layer with privacy protection and access control that sits on top of the three nodes — still needs to be built. This document assesses what is provided, defines exactly what is missing, proposes an architecture, and breaks the work into a prioritized, hackathon-sized task list.

The one-sentence goal: Build an aggregator service + web UI that lets an authorized clinician search all three hospitals at once (e.g., "hydrocephalus in patients under 10") while redacting PII according to the requester's role, and log every access.

4. Proposed Architecture

│                    Web UI  (:3000)                    │
│   login → search box + filters → results table        │
└──────────────────────────┬────────────────────────────┘
                           │  JWT on every request
┌──────────────────────────▼────────────────────────────┐
│              AGGREGATOR — FastAPI (:8000)             │
│                                                       │
│  /auth/login      issue JWT (role: clinician /        │
│                   researcher / admin)                 │
│  /api/search      q, age_min/max, sex, modality,      │
│                   body_part, date range, hospitals    │
│                                                       │
│  1. Auth middleware (verify JWT, extract role)        │
│  2. Fan-out: async httpx GET /api/studies × 3 nodes   │
│     (cache per node, refresh on TTL)                  │
│  3. Filter + rank results                             │
│  4. Redact per role  (name/DOB masked or dropped)     │
│  5. Audit log (SQLite or JSONL)                       │
└─────────┬──────────────────┬──────────────────┬───────┘
          │                  │                  │
   BCH :8001           MGH :8002          BWH :8003
   (untouched boilerplate — treat as legacy systems)

Key design decisions

  • Don't touch the nodes. Treat them as immutable legacy systems — that is the spirit of the challenge and impresses judges more than hacking the boilerplate.
  • Fetch-and-cache, filter in the aggregator. The nodes only offer "give me everything" (2,700 records total, tiny). Pull all studies with httpx.AsyncClient + asyncio.gather, cache in memory with a short TTL, and run search locally. Graceful degradation: if one node is down, return results from the other two with a per-node status flag.
  • Role-based redaction matrix (see Section 5). Redaction happens in one place — a single redact(record, role) function — so it is easy to demo and audit.
  • Age handling: PatientAge comes as 007Y / 011M / 005D. Normalize to a float in years at ingest so age-range filters work across pediatric and adult data.

8. Demo Script (for judging)

  1. Show a raw node: curl :8001/api/studies → point out exposed names/birthdates and no auth. "This is healthcare data today."
  2. Log in as researcher, search "hydrocephalus" → results from all 3 hospitals, PII redacted, pseudonymized IDs.
  3. Log in as clinician, same search → names visible, birthdate reduced to year. Same data, different lens.
  4. Kill the MGH node mid-demo → search still returns BCH+BWH with a degraded-status banner. Resilience.
  5. As admin, open the audit log → every query above is recorded.
  6. Close with the analytics endpoint (condition counts across hospitals, small buckets suppressed) → "research insight without ever moving or exposing patient data."

9. Setup on Your Laptop (Windows 11 + conda)

You already have conda, so skip the venv instructions in PRE_HACK_SETUP.md and use this instead. Run everything from PowerShell.

One-time setup

# 1. Create and activate a dedicated env (Python 3.11)
conda create -n borders python=3.11 -y
conda activate borders

# 2. Install dependencies
cd C:\Users\test\Projects\DataAcrossBorders
pip install -r requirements.txt

# 3. Extra packages you'll need for the aggregator (Section 6)
pip install httpx "python-jose[cryptography]" "passlib[bcrypt]"

Running the three hospital nodes (three PowerShell windows)

# Window 1 — Boston Children's
conda activate borders; cd C:\Users\test\Projects\DataAcrossBorders
$env:HOSPITAL_NODE="BCH"; uvicorn main:app --port 8001 --reload

# Window 2 — Mass General
conda activate borders; cd C:\Users\test\Projects\DataAcrossBorders
$env:HOSPITAL_NODE="MGH"; uvicorn main:app --port 8002 --reload

# Window 3 — Brigham and Women's
conda activate borders; cd C:\Users\test\Projects\DataAcrossBorders
$env:HOSPITAL_NODE="BWH"; uvicorn main:app --port 8003 --reload

Verify

curl.exe http://localhost:8001/health   # {"status":"healthy","node":"BCH"}
curl.exe http://localhost:8002/health   # MGH
curl.exe http://localhost:8003/health   # BWH

Note: in PowerShell use curl.exe (plain curl is an alias for Invoke-WebRequest). Interactive docs live at http://localhost:8001/docs (and 8002/8003). Once the aggregator exists it runs the same way on port 8000: uvicorn aggregator.main:app --port 8000 --reload. Task 12's run_all.ps1 launches all of this in one command — write it early, it pays off every restart.

10. Risks & Gotchas

  • PatientAge mixed units (Y/M/D) will silently break naive age filters — normalize first (BCH has neonates like 005D).
  • PatientName includes non-name values like Smith^BabyBoy — fine, but don't build name parsing that assumes real first names.
  • Windows: env var syntax for the nodes differs ($env:HOSPITAL_NODE="BCH" in PowerShell); put it in run_all.ps1 so it never bites during the demo.
  • The aggregator must not double-count: StudyIDs are unique per node but the same prefix scheme (BR-, etc.) appears across hospitals — always key on (hospital, StudyID).
  • Nodes allow CORS *, but the UI should still talk only to the aggregator — going straight to nodes from the browser would bypass your entire privacy layer (worth stating out loud to judges).
